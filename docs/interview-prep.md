## 二、STAR 面试稿

### STAR-1：把同步回包重构成异步可靠上报

- **S（情境）**：执行器原先同步 HTTP 回包结果，调度中心派发线程要等任务跑完才返回——慢任务拖住调度、手动触发页面长时间转圈，执行器一挂结果就丢。
- **T（任务）**：改成异步可靠上报，触发快返、结果不丢、重复投递不写脏终态，且要能讲清「为什么不是 exactly-once」。
- **A（行动）**：
  - 执行器只回 ACK（受理与否），结果经 RabbitMQ 回传；消息持久化 + publisher confirm，消费端 `@Transactional` 处理、**事务提交后才手动 ACK**（杜绝「ack 了但没落库」窗口），毒消息走 DLX。
  - 手动触发统一异步返回 RUNNING、页面轮询终态；超时判定下沉执行器，调度侧僵尸回收兜底。
  - 可靠语义选 **at-least-once + 业务幂等**：确定性幂等键 + `uk_execution_key`，收尾用 `finishIfRunning` 的 `status=RUNNING` 守卫，重复投递只生效一次。
- **R（结果）**：手动触发 ~209ms 快返；200 并发持续负载下结果队列深度 ≈ 1、无 RUNNING 滞留；终态只写一次。
- **追问预案**：为什么不用 exactly-once？→ 分布式下代价高，业务幂等 + 状态守卫已把「可能执行两遍」收敛成「终态只写一次」，取证上允许旧 attempt 迟到结果（已记 backlog B-06）。broker 挂了怎么办？→ 应用仍能启动，结果回不来靠僵尸回收标 TIMEOUT 进重试（ADR-019 如实记录）。

### STAR-2：用指标排除法定位压测拐点（最出彩）

- **S**：JMeter 压测 100→200 并发，吞吐只涨 33%（200→267 TPS）、P50 从 46ms 跳到 354ms。直觉判断是「服务端开始排队」，但**到底是执行器线程池、连接池还是 MQ？说不清**。
- **T**：把链路关键行为变成可观测指标，用数据定位真瓶颈，而不是猜。
- **A**：
  - Micrometer 埋点触发/派发 ACK 往返/结果/池排队与拒绝/队列深度，Prometheus 暴露、Grafana 看板；标签只用低基数枚举（绝不用 taskId，防时间线爆炸）。
  - 200 并发复跑做排除法：**执行器派发池 `executor_queued_tasks` 峰值 0、active ≤ 5**（demoHandler 秒回，池远未饱和）→ 排除执行侧排队；池拒绝 0、队列深度 0 → 排除 MQ 积压。
  - **五条链各计满 4000**（触发 dispatched / 派发 accepted / 执行 success / 回传 confirmed / 落库 applied），无丢失无拒绝，而触发请求 P50 已 440ms。
- **R**：瓶颈定位到**触发请求自身往返**（Tomcat/Hikari 连接排队 + 同步 ACK 往返），修正了「执行器排队」的直觉；复跑数据与对账入库（`docs/perf-200-rerun/`）可复现。
- **追问预案**：为什么池没排队还慢？→ 触发请求里有多次 DB 操作（existsRunning/fencing/落 RUNNING）+ 一次同步 ACK HTTP，Hikari max 10 在 200 并发下连接竞争，往返 latency 抬升；执行器 ACK 快、异步执行，所以派发池空。怎么优化？→ 调大 Hikari/触发池、ACK 与落库解耦、压测机与被测分离（诚实说当前是同机保守值）。

### STAR-3：鉴权编码绕过加固（B-10，体现安全敏感度）

- **S**：第 4 周给内部接口加了双向共享 token（常量时间比对、fail-closed）。复审时发现 filter 用 `getRequestURI()`（原始未解码）做路径匹配。
- **T**：确认并堵死一个理论绕过——百分号编码前缀。
- **A**：
  - 分析：`/api/v1/executors/%72egister`（%72=r）原始 URI 不含字面前缀 → filter 漏判放行，而 Spring PathPattern 按**解码后**路径照样映射到 register 处理器 → 不带 token 也能伪造注册/顶下线。
  - 修复：两处 filter 改 `getServletPath()`（容器解码、去 contextPath）；各补「编码前缀仍被拒」单测。
  - **起真实服务复验**（不只信单测）：编码路径无 token → 401，带合法 token → 200（证明编码路径确实路由到处理器，绕过真实存在且已被正确守卫）。
- **R**：绕过堵死，「加了鉴权」这句话经得起追问；ADR-020 补「按解码路径匹配」一节。
- **追问预案**：为什么单测不够？→ MockHttpServletRequest 的 servletPath 是手工设的，证明不了真实 Tomcat 在 PathPatternParser 下的解码行为，所以必须 live curl。管理 API 为什么不加鉴权？→ 演示体验取舍，仅限内网，生产交给网关（ADR-020）。

### STAR-4：拿到可信压测数字的两个坑（体现工程严谨）

- **S**：首轮压测错误率高、且压测库中途崩溃，数字不可信。
- **T**：排除环境与设计干扰，拿到能写进简历的可信数字。
- **A**：
  - **库崩溃**：本机 MySQL 8.1.0（Innovation 版）在 ~100/s 写入下 APPCRASH，首轮作废 → 切 Docker `mysql:8.0` LTS，三档 + 持续负载全程 0 重启。
  - **existsRunning 反压**：同任务并发触发被挡成 40900「任务正在执行中」，错误率被冲突主导。做对照实验：任务池 400 → 复用间隔 < 管道滞留 → **错误率 18.9%（全 40900）**；任务池 2500 → **0 错误**，两档吞吐几乎相同（冲突不压吞吐但污染错误率）。据此把任务池默认设为「线程数 × 40」覆盖 TPS × 滞留。
- **R**：50/100/200 并发 TPS 111/200/267、0 错误；把「压测要触发不同 taskId」这条设计约束量化成了可复现的对照实验。
- **追问预案**：为什么 40900 不压吞吐？→ 冲突请求很快返回（existsRunning 一次 DB 查询），耗时短，所以 TPS 不变但错误率上升——这正是「错误率」和「吞吐」要分开看的原因。

## 三、通用追问兜底（诚实边界）

- 「这是生产容量吗？」→ 不是。单机笔记本，应用/压测机/中间件同机竞争，数字是保守量级；demoHandler 秒回不含真实业务耗时；每档 10~15s 未做长稳与故障注入。
- 「token 安全吗？」→ 演示级：静态、无轮换/无 TLS，管理端点开放仅限内网；生产应换短期 token/mTLS + 网关认证。
- 「还有什么没做？」→ 告警规则/长期存储、队列深度精确监控口径、分片放大评估、若干低优先竞态遗留（B-02~B-09）都如实记在 backlog，不藏着。
